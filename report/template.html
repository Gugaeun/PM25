서울 PM2.5 시계열 예측 결과

서울 25개 자치구 측정소 평균 PM2.5를 1~24시간 뒤까지 예측합니다. naive·persistence·ARIMA·LightGBM을 기준으로 두고 PyTorch LSTM·1D-CNN을 같은 조건에서 비교했습니다.

데이터 2024-01 ~ 2025-12 (17,544시간)학습 2024 / 검증 2025-01~06 / 테스트 2025-07~12출처 서울 열린데이터광장 OA-23044 (확정 전 자료)

문제에서 접근까지

기존 서비스는 등급(좋음·보통 등)을 알려 주고, 이 프로젝트는 시간별 농도 수치를 예측합니다.

문제초미세먼지는 시간대별 변동이 커 사전 대응이 어렵습니다.
기존 방법현재 농도 확인(에어코리아·날씨 앱), 시간·일별 등급 예보
한계등급 단위라 구체적인 농도 수치와 변화 폭을 알기 어렵습니다.
이 프로젝트의 접근1~24시간 뒤 농도를 수치로 예측하고, 날씨 정보를 추가해 기준 방법과 비교합니다.

모델 비교

설정을 검증 구간에서 고르는 튜닝을 해도(LightGBM·LSTM·1D-CNN) 테스트 MAE는 −1.4%~+0.9% 변하는 데 그쳤지만 1D-CNN과 LSTM의 순위는 서로 바뀌었습니다(튜닝 전 1D-CNN 4.55 < LSTM 4.56, 튜닝 후 LSTM 4.50 < 1D-CNN 4.59). naive(어제 같은 시각)는 예측 시점과 상관없이 24시간 전 값을 쓰기 때문에 모든 horizon에서 오차가 같습니다. 그래서 짧은 horizon에서는 persistence(직전 값)가 훨씬 강한 기준입니다. LSTM·CNN·LightGBM+기상 값은 시드 3개를 평균낸 앙상블 예측입니다.

기상 변수를 넣으면 얼마나 좋아지나

PM2.5만 쓴 모델 대비 MAE 감소율, 테스트 구간

LSTM은 시드 3개의 평균이고 막대 끝의 선은 표준편차입니다. 기온·습도나 풍속 하나만 넣은 효과(1~2%)는 시드 간 차이(±0.08 MAE)와 비슷해서 단정하기 어렵습니다. 풍속벡터(풍향을 u, v로 변환)와 기상 전체 묶음은 두 모델 모두에서 일관되게 개선됐습니다. 입력 윈도우를 24·48·96·168시간으로 바꿔도 LSTM 오차는 로 거의 같았습니다.

실제값과 예측값

짧은 horizon은 실제값을 잘 따라가고, 길어질수록 고농도 정점을 놓칩니다.

고농도에서 실패하는 방식

편향 = 평균(예측 − 실제). 음수면 과소예측

테스트 구간에서 75µg/m³를 넘은 시간은 21시간뿐이라 "매우 나쁨" 행은 참고용입니다. 24시간 뒤 일평균 오차가 컸던 날은 11/24~25, 12/7, 12/17, 12/29로 모두 늦가을·겨울입니다.

고농도 탐지와 개선 시도

고농도 가중은 정답이 35를 넘는 샘플의 손실을 3배로, 분위수 0.7은 낮게 예측하는 것을 더 크게 벌점합니다. 시드 3개 앙상블, 테스트 2025-07~12. 가중치 3은 하나만 시도했고 튜닝하지 않았습니다. 서빙 모델에는 적용하지 않았습니다.

기상청 ASOS 연동: 검증 후 적용하지 않음

실시간 화면은 에어코리아에 기상 값이 없어 PM2.5 전용 모델을 씁니다. 기상청 ASOS 서울 관측소 값으로 기상 변수를 채워 보았지만 오차가 더 커졌습니다.

학습에 쓴 기상 값 (25개 구 평균, 이상적인 경우)5.83
ASOS 값 그대로7.40
ASOS, 바람은 평균비(0.64)로 보정6.30

PM2.5 전용 모델 (현재 실시간 모델)5.98

ASOS는 관측소 한 곳이고 학습 데이터는 25개 구 평균이라 정의가 다릅니다. 풍속은 평균 약 0.8m/s 차이가 나고, 풍향 성분(wind_v)은 상관이 0.14~0.33으로 거의 맞지 않았습니다. 기온·습도는 상관 0.97 이상으로 잘 맞았습니다. 학습에 쓴 기상 값을 넣어도 PM2.5 전용 모델 대비 개선은 약 2.5%여서, 실시간 화면은 PM2.5 전용 모델을 유지합니다(src/21_asos_check.py).

새 기간과 더 긴 학습으로 확인

결론은 학습 때 쓰지 않은 2026년 1~9월에서도 유지됩니다. 학습 기간은 5년까지 늘리면 좋아지다 멈추고, 고농도 놓침은 데이터를 늘려도 그대로입니다.

학습 기간별 (학습 곡선, 평가 2026-01~09)

분기별로 나눠 다시 확인한 결과 (walk-forward)

2025년 각 분기를 테스트로 두고 그 이전 전체로 학습했습니다(첫 분기는 학습 데이터가 2024년 1년뿐). 하이퍼파라미터는 분기마다 다시 맞추지 않았습니다. fold가 4개이고 분기 안의 사건 몇 개가 평균을 좌우하므로 개선율은 대략적인 범위로 읽어야 합니다.

ONNX 변환과 API 서빙

추론 시간은 CPU 1스레드, 요청 1건(배치 1) 기준 p50입니다. 모델은 시드 0 하나이고 모델 비교표의 수치와 다릅니다. 부하 테스트는 같은 컴퓨터에서 동시 1~32명으로 했고(results/load_test.md), 다중 worker에서 드물게 요청이 오래 응답하지 않은 경우가 있었습니다(원인 미확인). 별도 서버·실제 네트워크 성능은 아닙니다.

테스트 구간 실제 데이터 15건으로 호출해 평균 MAE 4.03, 응답 p50 약 3ms / p95 약 4ms를 확인했습니다(순차 호출, 네트워크 제외). 변수 누락·길이 오류는 422로 응답합니다.
